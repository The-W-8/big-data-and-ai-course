# 大模型上下文（LLM Context）自学笔记

> 概念英文名：Context / Context Window（上下文窗口）
> 所属分支：大模型推理机制
> 本笔记按"个人解释 → 核心机制 → 应用场景 → 易混淆边界 → 可核查资料"五部分组织。

## 1. 个人解释

一句话定义：**上下文是大模型在一次推理过程中能"看见"的全部信息，上下文窗口就是这块"视野"的容量上限（通常以 token 数计）。**

展开说：大模型不像人那样拥有持久的记忆，它每次回答问题时，其实是把你提供的所有信息——系统提示词、之前的对话历史、你上传的文档、检索到的资料、可用工具的定义——全部拼接成一段文本一次性"读"进去，再生成回答。这块一次性视野就是上下文。可以类比为一张**白板**：白板大小固定（窗口容量），每次提问都要把所有相关内容写上去，擦掉旧内容写新内容（多轮对话滚动截断），一旦某段信息没写上白板，模型就完全"看不见"它。窗口越大，能同时处理的信息越多；但白板写得越满，注意力就越分散，这也是后面"使用边界"要讲的问题。

## 2. 核心机制或组成

**（1）技术底座：自注意力机制。** 上下文的实现依赖 Transformer 的自注意力（self-attention）结构：序列中每个 token 都能"关注"其他 token，从而实现长程关联。这是《Attention Is All You Need》提出的核心机制。

**（2）上下文窗口的构成。** 一次推理中，上下文通常按顺序拼接以下内容：

```
[系统提示词] + [对话历史] + [检索资料/RAG 注入内容] + [工具/技能定义] + [当前问题]
```

**（3）关键性质：**

- **容量有限**：窗口以 token 计（如 128K、200K），所有组成部分共享这块容量，工具定义和检索内容都会挤占对话空间。
- **位置敏感（Lost in the Middle）**：斯坦福等机构的研究发现，模型对开头和结尾的信息利用最好，埋在长文本**中间**的关键信息会被显著忽略——"窗口大"不等于"用得好"。
- **成本随长度增长**：计费与延迟通常与输入 token 数正相关，无脑塞满上下文既贵又慢。
- **上下文学习（In-context Learning）**：在上下文中给出示例（few-shot）就能引导模型行为，无需重新训练——这是上下文最重要的应用性质。

## 3. 一个具体应用场景

**企业知识库问答（RAG，检索增强生成）——上下文机制的典型落地：**

某公司想让员工用自然语言查询内部规章。做法是：把规章文档切块并向量化存入数据库；员工提问"年假怎么折算"时，系统先检索出最相关的 3–5 个文档片段，**将这些片段拼进上下文**，再让模型"根据以下资料回答问题"。模型看似"知道"了公司规章，其实它只是**当下能看见**这些资料。这个场景同时暴露上下文的两面性：检索注入让回答有据可依（利用上下文学习）；但若检索回来的片段太多、关键条款被淹没在中间位置，答案质量会下降（Lost in the Middle 效应）——所以实践中要控制注入片段的数量与排列顺序。

## 4. 容易混淆的问题或使用边界

**易混淆概念对比：**

| 概念 | 生命周期 | 跨会话是否保留 |
| --- | --- | --- |
| 上下文（Context） | 单次推理内 | 否，每次请求重新拼接 |
| 记忆（Memory） | 跨多轮/多会话 | 需要外部存储（向量库等）人为实现 |
| 微调（Fine-tuning） | 永久写入模型参数 | 是，但改变的是"知识"而非"看见的输入" |

**使用边界与常见误用：**

- **上下文 ≠ 记忆**：关掉会话，模型对之前的内容一无所知；"长期记忆"都是应用层把历史存档后再选择性注入上下文实现的。
- **窗口大 ≠ 用得好**：长上下文中部信息利用率显著下降（Lost in the Middle），关键信息应尽量放在开头或结尾。
- **塞满上下文 ≠ 更聪明**：无关内容会稀释注意力并推高成本，"少而准"往往优于"多而全"。
- **上下文里有 ≠ 不幻觉**：即使资料已注入上下文，模型仍可能答错或编造，关键决策仍需人工核对原文。
